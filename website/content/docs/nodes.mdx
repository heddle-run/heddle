---
title: Steps
description: Reference for the step verbs available in heddle workflows.
---

Steps are the building blocks of a flow. Each step performs one piece of your workflow,
and declares exactly one **verb** — `agent`, `llm`, `tool`, `switch` or `use` — beside its
`name`. The examples below are entries in a flow's `steps` list; see
[Flows](/docs/flows) for how order, `then` and templates wire them together.

Every verb has a defined set of output keys, and those keys are the contract: a
`{{step.key}}` reference to anything a step does not write is refused when the document is
loaded. There is nothing a step writes that the format does not say it writes.

A sixth possibility is a step type a plugin registers, written with `use:`. It brings its
own executor and declares its own config schema and outputs. See [Plugins](/docs/plugins).

## agent

An LLM-powered agent that can call tools autonomously. The step sends the prompt to the
model, the model decides which tools to call, the tools execute, and their results feed
back to the model until it answers without requesting more tools.

```yaml
- name: researcher
  agent:
    model: main              # a name from `models`, or an inline config
    prompt: |
      You are a research assistant.
      Answer the user's question: {{inputs.query}}
    tools: [web_search]      # names from the document's `tools` map
    max_tool_rounds: 10      # optional; the runtime's default otherwise
```

`prompt` is the system prompt, and supports `{{ref}}` substitution. `tools` names entries
in the document's top-level `tools` map — a step only uses tools the document declares.

**Writes:** `result`, the model's final message as a string.

**What the model is sent.** heddle builds a system message from the `prompt` with its
references substituted, then a user message carrying, as JSON, exactly the values the
prompt references — `{"inputs.query": "hello"}` and nothing more. The agent sees precisely
what the document wired to it.

The agent runs at most `max_tool_rounds` rounds of tool calling (default 10); exceeding
that fails the run.

A tool input carrying a `default` is optional: it is left out of the schema's `required`
list, and if the model omits it the default is filled in before the tool runs. An input
without a default is required.

### Structured output

Declare `output` to get JSON instead of prose. The model is constrained to a JSON object,
and the step writes exactly the declared keys — extra keys in the answer are dropped, and
a missing key fails the run.

```yaml
- name: triage
  agent:
    model: main
    prompt: 'Classify the alert: {{inputs.alert}}'
    output:
      status: string
      note: string
```

**Writes:** the `output` keys — here `status` and `note` — instead of `result`.

Structure is either declared and enforced or absent, never guessed: an agent without
`output` writes only `result`, even when its answer happens to parse as JSON.

### Transforms

`transforms` attaches guardrails to the agent — plugin components that see the agent's
messages on their way to the model (`pre`) or back (`post`). `use` names the component
type; the rest of the entry is that transform's own config.

```yaml
- name: triage
  agent:
    model: main
    prompt: '...'
    transforms:
      - use: SecretScrub
        phase: both
        patterns: ['sk-[A-Za-z0-9]{16,}']
        replacement: '[REDACTED]'
```

A step with transforms also writes `transform_status` (`"ok"` or `"rejected"`), and
`transform_reason`, `transform_name` and `transform_phase` beside it — which a
[`switch`](#switch) step can route on. A `pre` transform that rejects skips the model call
entirely, and an agent carrying a `post` transform does not stream, because a token that
has reached a client cannot be recalled once the transform rejects the answer. See
[Plugins](/docs/plugins).

## llm

A single completion, with no tool-calling loop.

```yaml
- name: summarize
  llm:
    model: main
    prompt: |
      Summarize the following text in three bullet points:
      {{fetch.body}}
```

**Writes:** `text`, the model's response.

References substitute into the prompt as text: a string stays itself, a number or boolean
is stringified, an object or array is rendered as JSON. A reference nothing produces is a
load-time error, so a placeholder can never reach the model unfilled.

## tool

Executes an external tool directly, with no LLM involved. `tool` names an entry in the
document's `tools` map, and `with` carries the call's arguments — literals or templates.

```yaml
- name: fetch
  tool: fetch_api
  with:
    url: '{{inputs.url}}'
```

with the tool declared once, at the top level:

```yaml
tools:
  fetch_api:
    description: Fetch a URL and return the response body
    inputs:
      url: string
    outputs:
      body: string
```

**Writes:** the tool's declared `outputs` — and for a tool step they are contractual. The
runtime checks the executable's JSON against the declaration and fails the step on a
missing key or a mismatched type, so `{{fetch.body}}` downstream is a value, not a hope.

`with` is checked at load time too: an argument the tool does not declare is refused, and
so is leaving out a required input (one with no `default`). A value that is exactly one
reference keeps its type — `limit: '{{inputs.limit}}'` stays a number.

The tool's name must resolve in the flow's tool registry: an executable in `--tools-dir`,
or a tool a loaded plugin contributes, which exists nowhere on disk. See
[Tools](/docs/tools).

## switch

Routes execution by comparing one referenced value against `cases`. Case keys are values;
case targets are step or outcome names.

```yaml
- name: route
  switch: '{{classify.category}}'
  cases:
    tech: tech_steps
    science: science_steps
  else: done
```

The switch expression is exactly one template reference, compared by string equality.
`else` is required — a switch says where every unmatched value goes, and there is no
implicit default and no fallback scanning. Targets must appear later in the list, the same
forward-only rule every edge follows.

**Writes:** nothing. A switch routes; it produces no state.

A `switch` step takes no `then`: its `cases` and `else` are its routing.

## use

A plugin-defined step. `use` names a component type some loaded plugin provides; `with` is
that component's config, validated by the schema the plugin registered.

```yaml
- name: scrub
  use: RegexRewrite
  with:
    pattern: '\d{4}-\d{4}'
    replacement: 'XXXX'
    text: '{{researcher.result}}'
```

The plugin's executor receives the resolved `with` block — templates substituted — as its
input, not the run's ambient state.

**Writes:** the outputs the plugin's manifest declares for that component type, checked
against what the plugin actually returned, the same way a tool step is checked. Template
references into a plugin step's outputs validate against the manifest declaration.

Which plugin code answers to the type is the operator's decision (`--plugin`), never the
document's: a spec selects among what was already loaded. A document can pin the version
it was written against with top-level `requires`. See [Plugins](/docs/plugins).
