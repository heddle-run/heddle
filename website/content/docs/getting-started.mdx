## Installation

There is nothing to install. `npx` fetches the CLI and runs it:

```bash
npx @heddle/cli --help
```

Every `heddle` on this page can be spelled `npx @heddle/cli`. That is not a
shortcut around a missing install step — it is the shape of the thing. heddle is
a runtime you point at a document, so it belongs outside your project: no
dependency, no lockfile entry, nothing that has to be migrated when heddle
changes.

To keep it on the machine rather than fetching it each time, install it globally
via npm:

```bash
npm install -g @heddle/cli
```

Or via Homebrew:

```bash
brew install spichen/tap/heddle
```

Verify the installation:

```bash
heddle --help
```

heddle requires Node.js 18 or newer.

### Docker

There is also an image, if you would rather not install Node at all:

```bash
docker run --rm salahpichen/heddle --help
```

| | Docker Hub | GitHub Container Registry |
|---|---|---|
| CLI | `salahpichen/heddle` | `ghcr.io/heddle-run/heddle` |
| Server | `salahpichen/heddle-server` | `ghcr.io/heddle-run/heddle-server` |

One build pushes both, for `linux/amd64` and `linux/arm64`, with identical digests. Take whichever you prefer — Docker Hub caps anonymous pulls per IP, which is the difference a CI job feels first.

The examples ship inside the image, so there is a working agent to run before you have written anything. It needs a key, which the next section covers:

```bash
docker run --rm -e OPENAI_API_KEY salahpichen/heddle run \
  /opt/heddle/examples/research-assistant/flow.json \
  --tools-dir /opt/heddle/examples/research-assistant/tools \
  --input '{"query": "What is the Open Agent Specification?"}'
```

`-e OPENAI_API_KEY` with no value forwards the variable from your shell. Spelling it out as `-e OPENAI_API_KEY=sk-...` would put the key in your shell history and in the process list.

For your own project, `/work` is the image's working directory: mount your project there and every path stays the one you would have typed anyway.

```bash
docker run --rm -e OPENAI_API_KEY -v "$PWD:/work" salahpichen/heddle \
  run my-agent/flow.json --tools-dir my-agent/tools --input '{"query": "hello"}'
```

An alias is enough to make the rest of this page work unchanged:

```bash
alias heddle='docker run --rm -i -e OPENAI_API_KEY -v "$PWD:/work" salahpichen/heddle'
```

<Callout>
`-i`, not `-it`. A pty is one stream, so allocating one folds the progress output on stderr into the JSON result on stdout and `| jq` chokes on it. Chat mode is the exception, and it is spelled out below.
</Callout>

Tools run inside the container, so what matters is what the image can execute: `bash`, `python3` and `node` are all present. [The Docker guide](https://github.com/heddle-run/heddle/blob/main/docs/docker.md) covers the rest — file ownership, reaching a local model, `--safe` under a container runtime, and running the server image.

## Set an API Key

The scaffolded project uses OpenAI, so export a key before running anything:

```bash
export OPENAI_API_KEY=sk-...
```

Every provider needs a resolvable key, including local ones — see [LLM Providers](/docs/llm-providers) for how to point a flow at Ollama or vLLM instead.

## Create Your First Agent

Scaffold a new project:

```bash
heddle init my-agent
```

This creates:

```
my-agent/
├── flow.json      # Your workflow definition
└── tools/
    └── example_tool.sh   # A sample tool
```

The generated flow is a single agent wired between a start and an end node. It takes one input, `query`, and its system prompt interpolates that value with `{{query}}`.

## Run the Workflow

```bash
heddle run my-agent/flow.json \
  --tools-dir my-agent/tools \
  --input '{"query": "What is the Open Agent Specification?"}'
```

`--input` is a JSON object that becomes the run's starting state. It is not checked
against the start node: a key nothing declares is carried anyway, and a declared key you
omit is simply absent — a prompt referencing `{{missing}}` reaches the model with the
placeholder still in it. The final state is printed to stdout as JSON; progress and errors
go to stderr.

Add `--verbose` for per-node logging:

```bash
heddle --verbose run my-agent/flow.json --tools-dir my-agent/tools --input '{"query": "hello"}'
```

## Interactive Chat Mode

For debugging and exploration, use chat mode:

```bash
heddle run my-agent/flow.json --tools-dir my-agent/tools --chat
```

This opens a multi-turn session that re-runs the flow for each message, passing the conversation so far to the agent. Transcripts are written to `~/.heddle/conversations/`. Type `/exit` to quit.

Your message is bound to the first output declared on the start node, falling back to `query` if the start node declares none.

From the image, this is the one command that wants a TTY, so it takes `-it` rather than the alias above:

```bash
docker run --rm -it -e OPENAI_API_KEY -v "$PWD:/work" salahpichen/heddle \
  run my-agent/flow.json --tools-dir my-agent/tools --chat
```

Transcripts then live inside the container and leave with it. Mount a volume at `/home/node/.heddle` to keep them.

## Validate a Spec

Check your workflow before running it:

```bash
heddle validate my-agent/flow.json --tools-dir my-agent/tools
```

This validates the spec against the Agent Spec schema, compiles it, checks the graph, and
checks that an executable exists for every tool the flow names.

<Callout type="warn">
One case worth knowing in CI. A spec that does not parse exits 1, as does an invalid graph
and a tool a flow names that nothing provides. The exception is a graph heddle could not
*compile* at all: `validate` prints `Graph validation skipped` with the reason and exits 0,
so that a check which could not run is not mistaken for a fault. Read the output as well
as the status.
</Callout>
