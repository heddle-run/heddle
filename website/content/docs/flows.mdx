---
title: Flows
description: Learn how to define multi-step agent workflows as an ordered list of steps.
---

A flow is an ordered list of steps with the wiring implied: control flows from one step to
the next, and data moves wherever a `{{reference}}` names it. It defines the execution
order and data passing between the steps of your workflow.

Flows are written in YAML or JSON in **Weave**, heddle's own format. The default filename
is `weave.yaml`, and field names are `snake_case`. YAML and JSON are the two builtin
[input formats](/docs/plugins/formats); a plugin can add another wire format without
touching anything downstream of the parse.

## A complete flow

This flow takes a `query`, runs it through an agent with one tool, and returns a `result`:

```yaml
weave: 1
name: research-flow

inputs:
  query: string

models:
  main:
    provider: openai
    model: gpt-4o
    api_key: $OPENAI_API_KEY

tools:
  web_search:
    description: Search the web for information
    inputs:
      query: string
    outputs:
      results: string

steps:
  - name: researcher
    agent:
      model: main
      prompt: |
        You are a research assistant.
        Answer the user's question: {{inputs.query}}
      tools: [web_search]

outcomes:
  done:
    result: '{{researcher.result}}'
```

Everything is named once and referred to by name: `main` from `models`, `web_search` from
`tools`, `researcher` by the outcome that reads its output. There are no ids, no edge
lists, and no start or end nodes — the run starts at the first step, and ends at an
outcome.

A document whose whole job is one agent can drop `steps` entirely: a top-level `agent` is
shorthand for a single-step flow whose step is named after the document. That is what
`heddle init` scaffolds.

```yaml
weave: 1
name: researcher

inputs:
  query: string

agent:
  model:
    provider: openai
    model: gpt-4o
    api_key: $OPENAI_API_KEY
  prompt: 'Answer the question: {{inputs.query}}'
```

## Top-level keys

| Key | Required | Meaning |
|---|---|---|
| `weave` | yes | Format version, the integer `1` |
| `name` | yes | The flow's name: lower-case letters, digits, `_` or `-`, starting with a letter |
| `description` | no | Prose |
| `inputs` | no | What a run must be given, as a [schema map](#schemas) |
| `models` | no | Named model configs; see [LLM providers](/docs/llm-providers) |
| `tools` | no | Named tool declarations; see [Tools](/docs/tools) |
| `steps` | one of | The ordered list of steps |
| `agent` | one of | Shorthand: the whole document is one agent step |
| `outcomes` | no | Named terminal states and what each returns |
| `requires` | no | Plugin component type → semver range; see [Plugins](/docs/plugins) |
| `meta` | no | An opaque map, the only place unknown keys may live |

Unknown keys are an error everywhere else — at the top level, on a step, inside a schema.
The exceptions are `meta`, and the config of a plugin component (`use ... with` and a
transform's fields), which the owning plugin's schema judges.

## Inputs

`inputs` declares what a run must be given. A field without a `default` is required, and a
run missing one fails before anything executes; a field with a `default` is optional and
the default is filled in.

```yaml
inputs:
  alert: string
  limit:
    type: integer
    default: 5
```

`--input '{"alert": "..."}'` on the CLI, or the request's `inputs` over HTTP, is checked
against this declaration at the start of the run.

## Steps

`steps` is an ordered list. Each step has a required `name` — lower-case letters, digits
and `_`, starting with a letter — unique across steps and outcomes, since branch targets
resolve against both. The name `inputs` is reserved; it is the namespace flow inputs are
referenced through.

Beyond `name`, a step declares exactly one **verb**:

| Verb | What it does | Writes |
|---|---|---|
| `agent` | Runs an agent with tools | `result`, or its declared `output` keys |
| `llm` | Runs a prompt through a model, no tools | `text` |
| `tool` | Executes an external tool directly | The tool's declared outputs |
| `switch` | Routes execution on a referenced value | Nothing |
| `use` | Runs a plugin-defined step | What the plugin's manifest declares |

See [Steps](/docs/nodes) for detailed documentation on each verb.

### Control flow

Control flow defaults to **fall-through**: each step runs after the one before it, and the
last step falls through to the outcome `done`. A step may override that with
`then: <target>`, where a target is a later step or an outcome:

```yaml
steps:
  - name: triage
    agent: { model: fast, prompt: '...' }
    then: summarize      # skip past fetch

  - name: fetch
    tool: log_search
    with: { pattern: '{{inputs.alert}}' }

  - name: summarize
    llm: { model: fast, prompt: 'Summarize: {{inputs.alert}}' }
```

A `switch` step routes through its `cases` and `else` instead, and takes no `then`.

A `then` or `case` target must appear *later* in the list. Backward edges are reserved for
loops in a later format version, and refused by the validator today — so a Weave flow
always terminates, and fan-out does not exist: a step has exactly one successor unless it
is a `switch`, in which case it has exactly the successors its cases name.

## Templates

`{{ref}}` is the whole data-flow language, where `ref` is a dotted path:
`inputs.<field>` for a flow input, `<step>.<key>` for a prior step's output.

```yaml
prompt: |
  Service: {{inputs.service}}
  Evidence: {{fetch.matches}}
```

No expressions, no filters, no bare names. Literal `{{` is written `{{{{`.

Every reference is resolved at validation time: the producer must exist, the key must be
one the producer actually writes, and the producer must run on every control-flow path
that reaches the consumer. A reference to a key nothing writes, or to a step a path can
skip, is a load-time error rather than a placeholder reaching the model verbatim.

## State

There is no shared state bag. Each step's outputs live under its own name, and a step
receives exactly the values its templates reference. Two steps writing an identically
named output cannot collide, because the step name qualifies everything: `{{fetch.count}}`
and `{{verify.count}}` are different values.

<Callout>
This is a rule the format enforces, not a convention to follow. Earlier heddle releases
merged every node's outputs into one accumulated state, where identically named outputs
overwrote one another; Weave makes that unrepresentable.
</Callout>

## Schemas

Everywhere the format wants a schema — flow `inputs`, a tool's `inputs` and `outputs`, an
agent's `output` — it uses one shape: a map from field name to either a bare type string
or an object.

```yaml
inputs:
  alert: string                                # shorthand
  service:
    type: string
    description: The service the alert names.  # longhand
  limit:
    type: integer
    default: 5                                 # a default makes it optional
```

Types are `string`, `integer`, `number`, `boolean`, `array` (with `items`) and `object`
(with `fields`, recursively this shape). Field names are identifiers: lower-case letters,
digits and `_`, starting with a letter.

## Outcomes

`outcomes` maps each terminal state to the payload the run returns when it ends there.
Payload values are literals or templates:

```yaml
outcomes:
  done:
    note: '{{triage.result}}'
  handoff:
    note: '{{triage.result}}'
    reason: needs-human       # literals are fine
```

The run's final output is the payload plus `outcome: <name>`, so a caller always learns
which way the flow ended. `outcome` is therefore not yours to write in a payload.

If `outcomes` is omitted, the document gets an implicit outcome `done` that echoes what
the run accumulated — for a one-agent flow, the agent's own output. A step falls through
to `done` by default, so a document that defines `outcomes` without `done` must give its
last step an explicit `then`.

## Execution

When you run a flow, heddle:

1. Parses the YAML/JSON and checks the document's own shape — strictly, unknown keys
   refused
2. Resolves it: every branch target lands, every template reference names a real producer
   on every path, every plugin component is provided and validated by its plugin's schema,
   every `requires` range is satisfied
3. Compiles the graph and walks it, one step at a time, until an outcome is reached
4. Prints the outcome's payload, plus `outcome`, as JSON on stdout

Both validation passes run at load time, before any process starts and before any model is
called. `heddle validate` runs everything up to execution, and a flow that validates is a
flow that starts: a branch with no target, a placeholder nothing fills, a tool argument
the tool does not take — all of it fails at load rather than mid-run.

### Runner defaults

| Setting | Default |
|---------|---------|
| Max steps executed per run | 50 |
| Total run timeout | 5 minutes |
| Max tool rounds per agent | 10 — a step's own `max_tool_rounds` overrides it, as does `--max-tool-rounds` on the CLI |
| Tool execution timeout | 30 seconds |

The step limit, the run timeout and the tool timeout are fixed and not currently
configurable from the CLI. Exceeding the step limit or the run timeout fails the run with
an error.
